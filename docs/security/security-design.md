# Bank Agent 安全设计

## 1. 安全目标

Bank Agent 的核心原则是：模型可以理解和建议，但不能成为身份、权限、金额、风险等级或最终执行事实的权威。所有银行事实来自中端 Service/Fineract；所有写操作由确定性策略、Action 状态机、结构化确认、必要的 OTP、幂等和结果核对控制。

比赛版不开放 Shell、SQL、文件系统、任意 HTTP、代码执行、通用插件或模型生成 DAG。若未来增加代码执行，必须另行设计隔离容器、最小文件系统、网络出口、资源配额和审计，不能复用当前进程权限。

## 2. 资产、参与方与信任边界

| 资产 | 权威来源 | 主要风险 |
| --- | --- | --- |
| 登录身份和会话 | 中端 PostgreSQL + Bearer Token | 伪造身份、令牌重放、跨用户访问 |
| 余额、账户、流水、Hold 和转账 | Fineract | 重复扣款、结果不明、越权账户、伪造成功 |
| Action、确认、OTP、任务和审计 | 中端 PostgreSQL | 状态绕过、并发竞争、幂等冲突、敏感日志 |
| 卡片、订阅、分类和语义元数据 | 中端 PostgreSQL | 介质信息泄露、错误归类、越权修改 |
| 用户自然语言和模型输出 | 不可信输入 | Prompt Injection、工具滥用、幻觉、敏感信息外发 |
| Demo 商户与外部模型 | 受控外部依赖 | 供应商不可用、超时、数据边界误解 |

信任链为：`React → 认证中端 API → Service/Policy/Action → Fineract`。React、用户文本、模型、Tool 参数和客户端选择都不是授权依据。Tool 只能调用注入的 Service，不能直接持有 Fineract 管理凭据。

## 3. 身份、授权与数据隔离

- 身份只从认证 Token 解析，Agent Tool Schema 不接受 `user_id`、`client_id` 或租户；
- 中端每次读取账户、联系人、卡片、持有、订阅、报告、任务和 Action 时重新校验本人归属；跨用户资源统一隐藏为 404；
- 多候选使用会话内不透明 `option_ref`，选择回传后重新解析并校验归属与当前状态；
- 模型可见账户只用末四位或临时引用，完整内部 ID 不进入自然语言 Tool 参数；
- 前端路由保护只改善体验，真正权限始终由 API/Service 执行。

## 4. Agent 与 Prompt Injection 防线

1. 路由模型只能提出领域候选，中端用固定白名单和独占规则裁决；
2. 每轮只装配获准领域的 Prompt/Tool，未装配工具无法被模型调用；
3. Tool 名称、参数 Schema、累计调用次数和混批规则在执行前验证；
4. 订阅和生日任务必须单独请求，不能借组合请求扩大能力；
5. 银行精确结果通过本人私有结果/结构化事件给前端，模型只看到安全摘要；
6. Prompt Injection 规则只记录规则 ID，不保存恶意原文；
7. 10 分钟内累计 5 次敏感输入、注入或确定性权限失败后，Agent 写 Tool 锁定 15 分钟；普通只读 API 保持可用；
8. 无 Tool 结果时不得生成余额、交易事实或成功结论；模型失败不能覆盖已持久化 Action/任务状态。

## 5. GREEN / YELLOW / RED

| 级别 | 用户体验 | 确定性控制 |
| --- | --- | --- |
| GREEN | 直接查询本人事实 | Token、归属、Tool 白名单、Service 校验、私有结果通道；订阅页面只读查询属于此级 |
| YELLOW | 展示不可变摘要，用户点击确认 | `request_hash`、Action 状态、幂等键、执行前快照重验；对话订阅查询属于此级，不要求 OTP |
| RED | 摘要确认后完成 OTP | YELLOW 全部控制 + OTP 有效期/错误次数/重放防护 |

模型不能降低风险等级。普通转账风险按上海自然日累计金额由中端计算；定存申购/赎回、卡片敏感操作和生日任务授权固定为 RED。自然语言“确认”“我已验证”不改变 Action 状态。

订阅列表、详情、续费预测、提醒规则和预算规则在聊天中先生成固定条件及来源会话的 `subscription_query` YELLOW Action；只有用户点击聊天结果卡中的“确认查询”后，中端才查询并保存本人私有结果。确认前不读取订阅业务数据、不创建结果快照，查询 Action 有效期为30分钟，修改条件须重新发起。Action 确认不要求 OTP。用户直接进入订阅前端页面时，仍通过登录认证和本人归属校验直接执行只读 GET；客户端不能以页面来源字段获得额外权限。扫描、规则写入和取消订阅沿用各自既有流程。

## 6. 写操作完整性与恢复

- 浏览器一次提交生命周期固定 `Idempotency-Key`，相同键异参返回冲突；
- Action、计划发生项、生日节点和 Fineract 命令使用稳定键；
- 执行前重新读取本人归属、余额、状态、版本、限额和授权快照；
- 多 Worker 使用用户行锁、业务行锁、租约、乐观版本和唯一发生键防重；
- 上游响应不明进入 `RECONCILING`，只读核对核心事实，不换键盲重发；
- 已确认成功的资金操作不提供伪删除；取消只影响尚未执行部分；
- 生日任务暂停保留 Hold，取消释放未消费 Hold，已成功采购不自动退款。

## 7. OTP、登录与熔断

- 访问/刷新令牌轮换，退出撤销当前会话；
- 登录连续失败达到门槛后临时锁定；
- OTP 为随机六位、5 分钟有效、只能用于关联 Action，重发使旧码失效；
- OTP 连续 5 次错误锁定 15 分钟且不能通过重发清零；
- development 本人收件箱必须显式开启，非 development 禁止；生产短信通道尚未接入时 RED 操作明确失败；
- Agent 写熔断与登录/OTP 锁分离，避免攻击期间禁止用户查看本人只读事实。

## 8. 隐私、秘密与日志

- `.env`、虚拟环境、数据库备份、模型工件和 `.runtime` 报告不进入 Git；
- 密码使用 Argon2 哈希；Demo 完整卡号使用 AES-GCM 加密，密钥不入库；
- OTP、密码、Bearer/API Token 和完整卡号在聊天入库及模型调用前拒绝；
- 审计递归脱敏秘密字段，不保存模型内部推理、完整原始流水或私有分析明细；
- 精确余额、交易、财富和订阅结果通过本人授权的 no-store 接口读取；
- 外部模型 tracing 在银行链路关闭，真实评估报告不记录 API Key。

## 9. 审计与可追踪性

关键链路记录用户、traceId、会话/Run、领域、Tool、脱敏参数、策略、风险、Action、确认、OTP、执行、核对、资源类型和资源 ID。用户页面只展示友好摘要、时间、状态、失败原因和可复制 traceId，不透传内部 JSON。安全事件与会话内容分离；删除/过期对话不会删除安全审计。

## 10. 外部依赖和 Demo 边界

- Fineract 是核心账本事实来源，但本地 development 可关闭 TLS 验证；生产必须使用受信证书；
- 硅基流动/DeepSeek 是不可信外部推理服务，超时或非法输出不得变成业务成功；
- 卡组织、商户网络、订阅取消、花店/蛋糕店均为明确标注的 Demo Adapter；只有相关成功资金变动由 Fineract 证明；
- 不连接真实银行卡网络、短信、人脸、通讯录、日历或真实第三方会员系统；
- Demo Reset、Seed 和真实资金探针均需维护人员明确授权并限定隔离资源。

## 11. 验证要求

安全声明必须同时有自动化和隔离真实栈证据：跨用户隔离、Tool 白名单、注入、敏感输入、确认/OTP、幂等、并发、响应丢失、Worker 重启、Fineract/模型不可用、SSE 断线和浏览器恢复。版本化评估集至少包含 120 条六场景功能样本和 30 条安全样本；路由功能门槛 95%，安全样本 100%。未执行的真实模型、真实资金或浏览器验证必须明确标记，不能由 Mock 结果替代。
