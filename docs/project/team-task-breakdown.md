# 三人团队功能任务拆分

> 本文档定义当前非 Agent 阶段的代码最小单元、三人业务边界、任务依赖和完成标准。
> 产品与系统需求以 `docs/requirements/frontend-backend-requirements.md` 为准；全局阶段与实时状态以 `docs/project/master-plan.md` 为准。
> LangGraph、LLM、Prompt、Tool、对话协议和跨场景 DAG 属于后续 Agent 阶段，不是本文任务的完成前提。
> 成员 A 后续 Agent 纵向切片已经另行登记在 `docs/project/agent-member-a-task-breakdown.md`，不得用其 Action 创建状态替代本文普通业务真实执行验收。

## 1. 代码实现的最小单元

最小单元是一个可独立运行、测试、评审和演示的“用户能力切片”（Use-case Slice）。普通银行能力必须从页面贯穿到真实数据来源，而不是按前端、后端或数据库分成互相等待的半成品。

例如“本人账户互转”是一个完整最小单元：

```text
用户选择转出账户、转入账户、金额和备注
        ↓
React 校验并携带固定 Idempotency-Key 提交
        ↓
中端鉴权、账户归属校验、风险分级和 Action
        ↓
用户确认或 OTP
        ↓
Fineract 执行真实资金划转
        ↓
两边流水标记为内部转账，账单统计排除收入/消费
        ↓
页面恢复最终状态，审计和自动测试通过
```

以下内容不能单独算完成功能：

- 只有页面或 Controller；
- 只有数据库表或迁移；
- 只有 API Schema；
- 只有接口但没有权限、错误和测试；
- 页面依赖硬编码用户、账户、金额或状态；
- 资金结果没有来自 Fineract；
- 只完成 Agent Tool，但普通 Web App 无法独立使用。

## 2. 每个最小单元的完成标准

每个任务必须同时具备：

1. 对应的稳定需求编号和明确用户操作；
2. 页面或可复用交互组件，包括加载、空数据、失败和重试状态；
3. API 请求/响应和统一错误契约；
4. Service 中的确定性业务规则和本人资源归属校验；
5. 明确的数据表或 Fineract 事实来源；
6. GREEN/YELLOW/RED 风险等级；
7. 单元、集成或端到端测试；
8. traceId、Action 和 Audit 中适用的追踪记录；
9. OpenAPI、需求、部署和文件台账中适用的同步更新；
10. 可重复的人工验收步骤和结果证据。

写操作还必须具备：

- 在一次提交生命周期内固定的幂等键；
- 适用时创建 Pending Action；
- 执行前重新校验归属、状态、限额和余额；
- 明确的确认或 OTP；
- 重复请求不会重复执行；
- 超时或结果不明时只核对，不盲目重放；
- 执行前后中端状态、Fineract 余额/流水和审计断言。

一个 PR 原则上只交付一个用户能力切片，公共重构除外。Agent 阶段未来接入同一 Service 时另开任务，不回头改写已验收的资金规则。

## 9. PR 与任务粒度

推荐分支和 PR 命名：

```text
feat/A-04-internal-transfer
feat/B-07-subscription-detection
feat/C-06-purchase-risk-assessment
test/A-14-demo-card-transaction
fix/A-01-schedule-deadlock
```

PR 必须写明：

- 对应需求编号和任务 ID；
- 用户操作与验收结果；
- 风险等级和 Action/OTP 行为；
- 修改的页面、API、Service 和数据表；
- 兼容性或迁移影响；
- 测试命令、结果和真实栈验证范围；
- 是否需要其他成员迁移数据或更新调用方式；
- 是否同步了 OpenAPI、需求、部署和文件用途台账中适用的内容。

如果一个 PR 同时包含多个无关任务 ID，应拆分后再评审。
