## 1. 决策优先级

发生冲突或不确定时，按以下顺序决策：

1. 赛题原文中的硬要求：权限分级、安全机制、意图理解、任务规划、DAG、中断/回退/人工接管和作品材料；
2. 用户在当前对话中明确确认的范围与边界；
3. 当前代码、数据库迁移和真实验收证据；
4. 本文的实施设计；
5. 历史计划、旧技术栈说明和早期任务拆分。

赛题要求“至少覆盖 3 个核心场景，鼓励全覆盖”。本项目选择覆盖全部 6 个场景，但不以牺牲权限、安全和真实执行为代价。赛题没有要求微服务、多 Agent、通用工作流编辑器或任意代码执行，因此这些能力不进入比赛版本。

## 2. 比赛完成标准

完整 Agent 必须同时满足：

- 用户以自然语言表达需求，支持模糊表达、省略上下文和多候选消歧；
- Agent 能选择正确的业务 Tool，并仅通过 Banking Service 访问银行能力；
- 余额、流水、账户状态和资金执行结果来自中端/Fineract，不由模型生成；
- GREEN 操作自动执行，YELLOW 操作结构化确认，RED 操作强验证；
- 自然语言“确认”“忽略规则”等文本不能替代确认按钮、OTP 或确定性权限判断；
- 复杂任务形成可见的子任务 DAG，并支持暂停、恢复、失败重试、回退和人工接管；
- 所有关键操作具备 traceId、决策链、Tool 调用、权限结果、Action、验证、执行和最终状态审计；
- 连续失败、异常频率或重复验证失败能触发确定性安全锁；
- Web 端是完整演示入口，统一 Agent API 可供未来 APP/IM Adapter 复用；
- 六类场景、权限、安全和 DAG 均有自动化与真实隔离环境证据；
- 简介、架构、算法、安全、自评、README、部署、测试、PPT 和视频材料齐全。

## 4. 目标架构

```text
React Web / Future APP or IM Adapter
                  ↓
       Unified Conversation API + SSE
                  ↓
 Conversation Service / Trusted Context
                  ↓
 Trusted Domain Router ──→ Domain Agent Graphs
                  ↓                    ↓
            Read Tools            Write Request Tools
                  ↓                    ↓
          Banking Services      Policy + Action State Machine
                  ↓                    ↓
            Fineract Adapter ← Confirmation / OTP / Reconcile
                  ↓
          Apache Fineract + PostgreSQL

横切能力：Audit、Security Events、Idempotency、Trace、Rate Limit、Eval
```

架构约束：

- 保持单 Agent + 按需领域装配，不引入多 Agent；
- Router 只能从中端白名单选择领域，用户文本不能直接启用 Tool；
- Tool 只调用现有 Service，不直接拼装 Fineract 请求；
- LLM 只负责理解、澄清、参数提取和候选计划，不负责权限和最终执行；
- 写 Tool 只创建 Action、任务草稿或授权请求，不能直接移动资金；
- 精确金融结果通过认证后的私有结果或业务 API 给前端，模型只看到最小摘要；
- 银行事实不写入长期记忆；每次展示和执行前重新查询、校验和核对；
- 不开放任意代码执行。比赛版本不存在模型生成代码的执行入口，因此不伪造“沙箱”；若未来增加，必须使用独立受限容器。

## 5. 统一对话与 Agent 协议

### 5.1 会话与消息

新增服务端会话，默认保留 30 天并允许用户主动删除：

- 会话只属于当前登录用户；
- 保存用户消息、最终助手文本、结构化事件和运行状态；
- 不保存 Token、密码、OTP、完整卡号、模型内部推理或完整私有 Tool 结果；
- 传给模型的上下文限制为最近 8 条用户消息、可信槽位和必要的安全摘要；
- 联系人、账户、卡片、产品候选使用会话内不透明引用，不能用客户端提交的内部 ID 直接授权。

兼容保留 `POST /api/agent/messages`，新前端使用：

| 方法与路径 | 用途 |
| --- | --- |
| `POST /api/agent/conversations` | 新建会话 |
| `GET /api/agent/conversations` | 查询本人会话 |
| `GET /api/agent/conversations/{id}` | 恢复消息、事件和当前任务 |
| `DELETE /api/agent/conversations/{id}` | 删除本人对话内容 |
| `POST /api/agent/conversations/{id}/messages` | 提交消息并创建 Agent Run |
| `GET /api/agent/conversations/{id}/events` | SSE 进度、文字和结构化事件 |
| `GET /api/agent/runs/{runId}` | SSE 断开时只读恢复运行状态 |

Agent Run 由独立 worker 处理，避免外部模型慢请求阻塞 API 或资金计划 worker。SSE 支持 `Last-Event-ID`，前端断线后从最后事件继续，不重新提交写请求。

### 5.2 统一事件

所有事件包含 `event_id/conversation_id/run_id/trace_id/type/created_at/data`。比赛版本支持：

- `TEXT_DELTA`、`TEXT_COMPLETE`；
- `CLARIFICATION_REQUIRED`；
- `ANALYSIS_READY`；
- `NAVIGATION_REQUIRED`；
- `ACTION_CREATED`，并兼容当前领域专用 Action 事件；
- `CONFIRMATION_REQUIRED`、`VERIFICATION_REQUIRED`、`EXECUTING`；
- `TASK_CREATED`、`TASK_UPDATED`；
- `SUCCESS`、`ERROR`、`CANCELLED`。

事件只是展示和导航信息。前端打开 Action/Task 页面后必须重新读取服务端状态和当前用户权限，不能把事件本身当作授权。

### 5.3 澄清与消歧

以下情况必须追问，不能猜测：

- 联系人同名、别名多匹配或手机号不唯一；
- 多个可付款账户且用户未指定；
- 多张卡片、多个定存产品或多个持有；
- 金额、日期、周期、转入账户或风险测评缺失；
- 跨场景任务的生日日期、鲜花金额、蛋糕金额或付款账户缺失。

前端候选按钮提交会话内 `option_ref`；中端映射真实资源后仍需重新做本人归属和状态校验。

## 6. 六类业务场景设计

### 6.1 智能转账

覆盖：余额、流水、联系人姓名/手机号/别名检索、普通转账、本人互转、一次/日/周/月定时转账和 AA 收款。

- 查询为 GREEN；
- 单个自然日累计不超过 1000 元的普通转账为 YELLOW；
- 超过 1000 元、计划预授权和赛题指定的强风险操作为 RED；
- 所有资金请求使用固定幂等键、Action、执行前复核和只读核对；
- 真实验收必须断言 Fineract 双边余额、流水、Action、审计和重复提交不重复扣款。

### 6.2 账单分析

覆盖：单/全账户分类统计、最大消费、收入支出趋势、异常候选、月报和年报。

- 查询为 GREEN；
- Agent 通过 `AnalysisResult` 返回精确卡片，模型只描述结果类型和完整性；
- 异常只作为候选，不自动冻结、撤销或声称欺诈；
- 月/年报告显示范围、账户集合、数据截止时间、规则版本和非原子快照提示；
- 用独立标注集报告准确率、召回率和误报，不以合成排序代替真实质量结论。

### 6.3 理财操作

只覆盖 Fineract 原生定期存款：产品目录、比较、推荐、风险评估、申购、持有、赎回报价和整笔赎回。

- 产品查询、比较、持有和收益查询为 GREEN；
- 五题风险测评必须由用户在结构化页面完成，模型不得代答；
- 每笔申购使用一份 15 分钟内、未消费的测评；
- 超出承受等级的产品由确定性代码拒绝；
- 申购和赎回为 RED，Tool 只创建 Action，部分赎回明确不支持；
- 精确本金、利率、报价和持有信息不进入模型 ToolMessage。

### 6.4 卡片管理

覆盖普通 Demo 借记卡申请、激活、限额、线上/POS/ATM/境外开关、锁定、解锁、挂失、补卡和安全查看。

- 查询掩码卡信息为 GREEN；
- 申请、降额、关闭渠道和锁卡为 YELLOW；
- 激活、提额、开启渠道、解锁、挂失、补卡和安全查看为 RED；
- 完整 Demo 卡号只在成功 OTP 后由专用接口短时返回，永不进入模型、URL、Action 或审计；
- Demo 商户消费真实进入 Fineract，但 UI 明确说明卡组织与商户网络为比赛模拟。

### 6.5 订阅与代扣管理

覆盖订阅识别、续费提醒、候选证据、核实/忽略和 Demo 取消。

- 只读提醒可显示数量和到期摘要；按赛题要求，查看具体订阅明细和取消均进入 YELLOW 结构化确认；
- Agent 不从金额或普通备注猜测商户，复用确定性识别证据；
- 取消只作用于明确标注的 Demo 商户 Adapter，不冒充真实第三方取消；
- 取消后 Demo 扣费必须拒绝并审计；
- 新增 `subscriptions` 领域 Tool 和确认事件，不复用账单域隐式执行写操作。

### 6.6 跨场景联动

赛题演示固定为一次性“爱人生日”任务：

```text
读取/确认生日事件
        ↓
校验付款账户和鲜花/蛋糕金额
        ↓
展示完整 DAG 并完成一次 RED 授权
        ↓
生日当月通过 Fineract Hold 预留两笔资金
        ↓
生日前两天分别释放对应 Hold
        ↓
向 Demo 花店和蛋糕店真实转入 Fineract 资金
        ↓
生成站内完成/失败通知
```

实现规则：

- 个人事件可由用户在对话中新增，也可由 Seed 预置；Agent 不读取真实通讯录或日历；
- 用户必须明确生日日期、鲜花金额、蛋糕金额和付款账户，模型不得自行拆分预算；
- 只生成固定白名单 DAG，不提供通用 DAG 编辑器；
- 一次 OTP 授权完整计划，但每个节点独立保存风险结果、金额、商户、时间和不可变指纹；
- 暂停不释放 Hold；取消释放未消费 Hold；已完成购买不自动退款；
- 核心响应不明进入 `RECONCILING`，禁止更换幂等键重付；
- 部分成功进入 `WAITING_USER/PARTIAL`，支持重试失败节点、取消剩余节点或人工接管；
- Mock 外部下单与真实核心资金边界必须在 UI、文档和答辩中明确。

## 7. 权限、安全与审计

### 7.1 确定性权限

| 级别 | 行为 | 代表能力 |
| --- | --- | --- |
| GREEN | 意图明确后自动查询 | 余额、流水、账单、产品、持有、掩码卡状态 |
| YELLOW | 展示不可变摘要并点击确认 | 小额转账、订阅明细/取消、卡申请、锁卡 |
| RED | 展示摘要、确认并 OTP | 大额转账、计划授权、卡高风险操作、定存申购/赎回、跨场景任务授权 |

风险等级、日累计、Action 状态、验证次数、权限和最终执行全部由中端确定性代码处理。模型输出不能降低风险等级。

### 7.2 赛题安全要求

- **幻觉防护**：没有 Tool/私有结果就不回答银行事实；Action 创建不等于执行成功；失败或不完整必须明确展示；
- **注入防御**：域白名单、参数 Schema、本人资源归属、Action/OTP 和 Service 复核独立于 Prompt；
- **操作审计**：记录用户、trace、会话、领域、Tool、脱敏参数、策略、风险、确认、验证、执行和核对结果；
- **异常熔断**：沿用 5 次 OTP 失败锁定 15 分钟；新增安全事件与写操作锁，10 分钟内连续 5 次验证/权限失败或异常重复写请求时锁定写能力 15 分钟，查询仍可用；
- **沙箱边界**：比赛版本禁止任意代码和 Shell Tool；如未来增加代码执行，必须另行设计隔离容器、网络和文件系统限制。

所有审计禁止记录密码、Token、OTP、完整卡号、模型内部推理、完整原始流水和私有分析明细。

## 8. 数据与执行组件

统一基线已经包含账单报告 `0007`、订阅提醒 `0008` 和成员 A 幂等补充 `0009`。后续按职责新增：

- `0010`：`agent_conversations`、`agent_messages`、`agent_runs`、`agent_events`、`security_events`、`security_locks`；
- `0011`：`personal_events`、`orchestration_tasks`、`task_nodes`、`task_edges`、`task_events`、`fund_reservations`、`demo_orders`。

不新增第二套账户余额。资金余额、Hold、转账和交易流水仍以 Fineract 为事实来源。

后台进程分工：

- API 进程只处理 HTTP、认证、状态读取和提交请求；
- Agent Worker 领取 `QUEUED` Run，调用模型、Tool 和写入 SSE 事件；
- Banking Worker 继续执行定时转账，并扫描已授权 DAG 节点；
- 多 Worker 使用行锁、租约、唯一发生键和稳定幂等键防重；
- worker 重启后恢复未完成 Run/节点，不自动重放结果不明的资金请求。

## 10. 测试与真实验收

### 自动化层次

- Service 单元测试：权限、状态、金额、时间、边界和错误码；
- PostgreSQL 集成测试：真实事务、行锁、租约、并发、迁移往返和幂等；
- Agent 图测试：领域选择、Tool 参数、澄清、失败语义和输出忠实；
- API 测试：认证、会话、SSE、Action、Task 和跨用户隔离；
- 前端组件/E2E：桌面、390px、Chrome、Edge、刷新恢复和错误状态；
- 故障注入：Fineract/LLM 超时、响应丢失、worker 中断和 PostgreSQL 重连。

### 真实隔离环境

- 使用 `BANK-PROBE-*` 专属客户、账户、联系人和商户，不修改 Alice/Bob 等演示数据；
- 外部模型只接收合成姓名、金额和意图，并要求显式数据出境开关；
- 真实资金写入要求 development、本机 Fineract 和显式确认参数；
- 证据核对 Fineract 双边余额/流水、Action、Task、审计、trace 和幂等重放；
- 脱敏证据可以纳入版本控制，状态文件、Token、OTP、密码和完整卡号不得提交。

## 12. 明确不做

- 不连接真实银行卡组织、真实商户网络、短信、邮件或人脸服务；
- 不宣称 Demo 订阅取消等于真实第三方取消；
- 不建设通用 DAG 编辑器、开放式插件市场、多 Agent 或自动写代码系统；
- 不让模型直接访问数据库、Fineract、Shell 或文件系统；
- 不以固定前端数据、模型记忆或 Mock 余额替代银行事实；
- 不为了演示成功而绕过确认、OTP、权限、幂等或核对。

## 13. Definition of Done

项目只有在以下条件全部满足后才能宣称“完整 Agent 已完成”：

1. 六类场景都能从自然语言入口进入并形成真实、可恢复的业务闭环；

3. 至少一个生日任务 DAG 具备预留、等待、购买、通知、暂停、恢复、回退和人工接管；
4. 关键安全指标全部达到 100% 门槛；
5. PostgreSQL、前端、Playwright、模型评估和真实 Fineract 探针全部通过；
6. 没有未标注的 Mock、硬编码余额、内部 ID 泄露或敏感日志；
7. OpenAPI、部署、文件台账、总计划和测试证据同步；
8. 所有比赛提交材料齐全，并完成至少 3 次计时彩排。
